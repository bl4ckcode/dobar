## Latest backend update

- Date: 2026-11-26. Scope: [C06](../.specs/mvp-v0.1/C06-live-menu.md) menu authorization and [B07](../.specs/mvp-v0.1/B07-staff-invitation.md) invitation hardening; no migration, paths and response shapes unchanged. Tests: [menus](../be/tests/test_menu_authorization.py), [invitations](../be/tests/test_staff_invite_authorization.py), [pending](../be/tests/test_pending_invitations.py); local SQLite with mocked services, not deployed, no PostgreSQL concurrency run.
- Menus: every `/menus` route now needs a login (401 without a token, 403 for a disabled user); on `main` they were public. Any logged-in user, customers included, may still read menus, items and trending data at any venue. Mutations need a permission at the venue that owns the menu (taken from the stored menu; `bar_id` query and `X-Bar-Id` are ignored): `menu:create` for create menu, add item and bulk add; `menu:edit` for update menu/item and `PATCH .../availability`; `menu:delete` for deleting. Others get 403 `Missing permission: ...`; an unknown menu is 404. Managers gain `menu:create` (owner/admin/manager create and edit, owner/admin delete). FE action: send the token on every menu call (the app already does) and expect 403 in the business editor. An anonymous caller (public menu, QR) would now get 401.
- Invitations: `POST /bars/{bar_id}/staff/invite` and the compatibility `POST /staff/invite` share one service. Both need `staff:manage` at that venue; the compatibility route previously let a manager without a custom grant invite, so that caller now gets 403 `Missing permission: staff:manage`. An inviter cannot assign a role above their own (owner stays owner-only). The contact must be a valid email or E.164 phone (422). A repeat invite for the same contact and role returns the existing invitation with the same code and a renewed 7-day expiry; a different role revokes the old one and issues a new one (409 if the old one ranks above the caller). An invitation never grants membership; only the verified recipient can accept. FE action: treat a repeated code as a resend, and handle 403 and 409.
- Staff changes: `PUT /bars/{bar_id}/staff/{id}/role` and `DELETE /bars/{bar_id}/staff/{id}` enforce the same rank rule and return 409 if the target's role changed while the request ran (reload and retry).
- Order status (B05, 2026-11-25): one transition table for the HTTP routes and `/ws/bar/{bar_id}/orders`; legacy `PUT /orders/{id}/status` needs `order:process` at the order's bar (404 otherwise); socket commands re-check it per command, and a disabled account now holds no permissions on sockets either; contention returns 409 `CONFLICT`. Open gaps (B05 BE-3/FE-2) live in the [B05 spec](../.specs/mvp-v0.1/B05-cashier-live-orders.md).
- Carried forward: `GET /home/` optional `display_name`, `promo_summary`, `nearest_venue` and per-bar `category`/`primary_promotion`/`promotion_text`; `GET /bars` listing mode (`q`, `min_rating`, `has_promotions`, `limit` ≤ 100, `offset`, `X-Total-Count`/`X-Has-More`) with the legacy unpaged order for old params; `CampaignCreative.promote_happy_hour`; `/me/benefits` and contact-change APIs ([dob_95](../be/migrations/versions/dob_95_contact_change_requests.py)), `PUT /me/profile` 409 on contact changes, `GET /orders/user/me` `bar_name`, `defer_payment` false for legacy callers, `/me/cards` needs a fresh PagarMe `token_`, `POST /checkins` needs [c05](../be/migrations/versions/c05_customer_checkins.py). Rollout: DPE → migrated BE → FE via CI/CD.
