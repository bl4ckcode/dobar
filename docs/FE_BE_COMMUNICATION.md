## Latest frontend update

- Date: 2026-11-08. Scope: Home, venue discovery and shell (Lovable `2a32eb05`). `GET /home/` is the only Home-entry request; FE reads the additive `display_name`, `promo_summary.total`, `nearest_venue` and per-bar `category`/`primary_promotion`/`promotion_text`, treats `distance_meters` as nullable, and shows a plain greeting when summary data is absent ([model](../fe/lib/features/home/domain/models/home_model.dart), [toolbar rules](../fe/lib/features/home/domain/home_toolbar.dart): venue prompt only when `nearest_venue.distance_meters` < 10 m, else `promo_summary.total` > 0, else greeting). Badges come only from `primary_promotion`; FE no longer searches promotion titles.
- Category pills open `/category/{bars|restaurants|clubs}` ([page](../fe/lib/features/venues/presentation/pages/category_venues_page.dart)), calling `GET /bars` in listing mode: `category` = `bar|restaurant_bar|night_club`, `limit=20`, `offset`, optional `latitude/longitude`, `max_distance` (≤ 50 km, location only), `q`, `min_rating`, `has_promotions`; reads `X-Total-Count`/`X-Has-More`. Search is debounced and stale responses are dropped.
- Shell mounts only the selected tab; Home results, per-tab scroll and Find search/panel/camera/destination/route live in [ShellSession](../fe/lib/core/session/shell_session.dart) (route redrawn from saved points, no directions request). Browsing never prompts for location; check-in explains in Portuguese, then requests it ([explainer](../fe/lib/features/location/presentation/location_permission_explainer.dart)).
- Compatibility: BE first; an older BE lacks the new fields (greeting only, badges hidden) and ignores the extra `/bars` params (no pagination headers, so FE shows one page). Carried forward: benefits/venues (`/me/benefits`), order `bar_name`, read-only contact edit, native-wallet probe stubbed. Tests: [toolbar](../fe/test/features/home/home_toolbar_test.dart), [bloc](../fe/test/features/home/home_bloc_test.dart), [category](../fe/test/features/venues), [shell](../fe/test/ui/shell/shell_lifecycle_test.dart). Device/browser acceptance unverified.

## Latest backend update

- Date: 2026-11-25. Scope: [B05](../.specs/mvp-v0.1/B05-cashier-live-orders.md) order-status hardening; no migration, paths and `OrderSchema` responses unchanged. Tests: [status updates](../be/tests/test_order_status_updates.py), [orders](../be/tests/test_orders.py); local SQLite with Redis stubbed, not deployed.
- `PUT /orders/{id}/status`, `PUT /bars/{bar_id}/orders/{id}/status` and `/ws/bar/{bar_id}/orders` commands share one transition table: `pending→confirmed|preparing|cancelled`, `confirmed→preparing|cancelled`, `preparing→ready|cancelled`, `ready→completed`; `completed`/`cancelled` terminal. New: `pending→preparing`. Legacy `confirmed` stays valid.
- Authorization: the legacy `PUT /orders/{id}/status` now needs an active membership with `order:process` at the order's bar (previously any authenticated user). Callers without it get 404 `ORDER_NOT_FOUND`, the same as for a missing order. The venue route keeps 403 without `order:process` and 404 for another bar's order. WS commands re-check `order:process` on every command.
- Writes are compare-and-set with the history row in the same transaction. Invalid transitions return 400 `BAD_REQUEST`; persistent contention returns new 409 `CONFLICT` (FE action: refetch the order or `/live` and retry). `order.status_changed` is published only after commit, and status writes never touch `payment_status`.
- Known gaps (B05 BE-3/FE-2): HTTP status changes are not yet delivered to sockets (order worker not started); `POST /orders/sync` ignores `status_change`, so FE must send queued status changes through the venue PUT (decision D2).
- Carried forward: `GET /home/` optional `display_name`, `promo_summary`, `nearest_venue` and per-bar `category`/`primary_promotion`/`promotion_text`; `GET /bars` listing mode (`q`, `min_rating`, `has_promotions`, `limit` ≤ 100, `offset`, `X-Total-Count`/`X-Has-More`) with the legacy unpaged order for old params; `CampaignCreative.promote_happy_hour`; `/me/benefits` and contact-change APIs ([dob_95](../be/migrations/versions/dob_95_contact_change_requests.py)), `PUT /me/profile` 409 on contact changes, `GET /orders/user/me` `bar_name`, `defer_payment` false for legacy callers, `/me/cards` needs a fresh PagarMe `token_`, `POST /checkins` needs [c05](../be/migrations/versions/c05_customer_checkins.py). Rollout: DPE → migrated BE → FE via CI/CD.
