## Latest backend update

- Date: 2026-11-08. Scope: C04 dependencies. Apply migration [dob_95](../be/migrations/versions/dob_95_contact_change_requests.py) (additive table) before this code. Tests: [profile dependencies](../be/tests/test_profile_dependencies.py), [wallet boundary](../be/tests/test_native_wallet_boundary.py); local SQLite only, no deployment.
- `GET /me/benefits` (auth): `{benefits[], active_count, currency}`. Kinds: `pro_coupon` (id `pro_coupon:YYYY-MM`, 5/month, no rollover; units `coupon`) and `cashback` (id `cashback_wallet`; `brl_cents` integers, `pending`). `status` is `active|unavailable` with `unavailable_reason` (`pro_required|allowance_exhausted|no_eligible_venues|zero_balance|pending_clearance`). Cashback `eligibility.venue_filter_supported=false`: redemption is wallet-wide today and the product rule is undecided.
- `GET /me/benefits/{id}/venues?limit&offset`: for `pro_coupon`, venues with an active, in-window, bar-funded `cashback` promotion plus promotion terms. 404 unknown or other-period id; 403 non-Pro; 409 for unavailable or cashback. Read-only: it never reserves or redeems. Checkout validation stays authoritative.
- `POST /me/contact-change {channel,new_value}` starts a 10-minute server challenge (one active per user and channel). `POST /me/contact-change/{request_id}/confirm {proof_token}` takes a Firebase ID token for the NEW contact (phone claim, or `email_verified` email), signed in within 5 min. It is single-use with 5 attempts. It re-checks uniqueness, applies the contact as verified, binds the new phone's Firebase uid, revokes all refresh tokens and returns fresh `access_token`/`refresh_token`. `/cancel` discards a pending request. Foreign ids return 404; replayed, expired or cancelled ids return 401.
- **Breaking-but-guarded:** `PUT /me/profile` returns 409 `CONFLICT` when `email`/`phone_number` differ from the stored value, with no partial writes. Identical values and name/avatar edits succeed and never touch verification.
- `GET /orders/user/me` adds optional `bar_name`. `DELETE /me/data` now also deletes `payment_cards`, `idempotency_keys` and `contact_change_requests`; retained categories are in [C04](../.specs/mvp-v0.1/C04-profile-privacy.md).
- Carried forward: `defer_payment` is false for legacy callers; `/me/cards` needs a fresh PagarMe `token_` and stores `card_`. `POST /checkins` needs migration [c05](../be/migrations/versions/c05_customer_checkins.py), and MongoDB location recovery falls back to the address. Profile responses include integer `id`. Rollout: DPE → migrated BE → FE via CI/CD; B02/B08 prerequisites stand.
