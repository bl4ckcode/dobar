# Using Dobar agent workflows from VS Code

Open the monorepo root in VS Code and choose an agent in your installed assistant. Give it an explicit outcome, scope, spec/issue, and skill paths. The agent reads those procedures, inspects the code, implements within scope, and runs checks. You decide when to move work to another agent. See the [workflow reference](AGENT_WORKFLOW.md) for policies and command details.

## What each piece does

| Piece | Purpose | Example |
|---|---|---|
| Spec | Desired behavior, acceptance criteria, dependencies and evidence status | `.specs/mvp-v0.1/B08-staff-invitation-acceptance.md` |
| Linear issue | A tracked assignment, discussion and scheduling context | DOB-91, backend work for B08 |
| Role | Responsibility and preferred model | `.agents/roles/backend.md` |
| Skill | Instructions an agent reads and follows | `.agents/skills/dobar-backend/SKILL.md` |
| Orchestrator | An agent following the product/orchestration procedure to clarify scope, order tasks and prepare handoffs | GPT using `dobar-orchestrate` |
| CLI handoff | A generated Markdown context package for a spec and role | `.agent-workflow/handoffs/B08-backend.md` |
| Implementer | The selected agent editing code and running affected checks | Cline or Sonnet following the backend skill |
| Verifier | An independent assessment of the current implementation against acceptance criteria | GPT following `dobar-validation` |

The orchestrator makes context-dependent decisions. The CLI handoff assembles existing information deterministically. Neither selects/launches another model automatically. A handoff can be written by the orchestrator or generated by the CLI; neither requires the other.

## What happens automatically today

When you explicitly instruct an agent to read named skills and implement a bounded task, it should do the reading, inspection, coding and local checks in that session. Skill discovery alone depends on the installed client and workspace configuration; listing the full `SKILL.md` paths in the prompt makes the required procedure explicit. Ask the agent to report which skills it used.

Reading a skill does not install tools, supply credentials, execute a script or create a background worker. Linear access must be available to that particular agent session. An authenticated terminal CLI and an assistant's connected Linear tool are separate access paths. If access is absent, the agent reports it and works from supplied issue text where possible; it cannot claim to have checked live Linear.

The CLI currently supports `validate`, `tickets export`, `tickets sync`, `handoff` and `verify`. Handoff generation reads local files; it does not inspect live Linear, resolve missing dependencies, implement, test or certify readiness. Feature ticket exports apply configured area/type labels; agent-driven issue creation must also follow the Linear skill's cycle policy. Live ticket writes need task authorization; read access does not authorize edits.

Automatic task branches/worktrees, commits, pushes and PRs belong to [P01](../.specs/platform/P01-development-pr-workflow.md) and are not implemented by these commands. Existing Git/deployment safeguards remain active.

## Choose the starting point

| Situation | Start with | What you ask for |
|---|---|---|
| Reproducible bug with understood expected behavior | Bug-fix agent plus affected-area skill | Reproduce, fix narrowly, run regression checks |
| Clear backend-only or frontend-only task | Scoped implementation role | Inspect dependencies, implement the assigned scope, test |
| Unclear requirements, several areas or unresolved contracts | Orchestrator, then cross-area planner | Clarify intent, order dependent tasks, prepare implementation briefs |
| Approved React export to translate | Heavy UI role | Inspect actual source/revision and implement Flutter using existing architecture |
| Implementation ready for assessment | Independent verifier | Assess criteria and evidence; report gaps separately |

One agent can handle several areas if explicitly assigned and equipped for them. A separate model for every skill is unnecessary. Area boundaries and actual dependencies determine the split. Do not start concurrent agents editing the same files without an explicit integration plan.

## Scenario 1: Implement an existing scoped issue directly

Choose your backend agent and paste:

```text
Implement the backend task DOB-91 for B08 in this repository.

Read AGENTS.md, be/AGENTS.md, the B08 spec, and these skills:
- .agents/skills/dobar-backend/SKILL.md
- .agents/skills/dobar-validation/SKILL.md
- .agents/skills/dobar-communication-docs/SKILL.md

Read DOB-91 and its parent/dependencies through available Linear access.
If access is unavailable, report that limitation and use the local B08
spec and pilot implementation tasks; identify any missing issue decisions.

Inspect the current code and dependency readiness, then implement the
backend acceptance scope. Preserve compatibility and user changes.
Prepare a frontend handoff for contract changes instead of expanding
into frontend implementation. Run relevant backend and contract checks.
Report changed behavior, criteria covered, and passed/failed/blocked/skipped
checks. Do not publish Linear updates, commit, push or deploy.
```

This authorizes implementation, rather than just a plan. The implementer can perform local reasoning and planning within the assignment. It only needs a separate planning handoff when an unresolved dependency or material contract/product decision prevents safe implementation.

The author's local testing is necessary evidence, but it is not an independent review. Use scenario 5 when the change is ready to assess.

## Scenario 2: Orchestrate a feature spanning UI and backend

Choose GPT/product and paste:

```text
Use .agents/skills/dobar-orchestrate/SKILL.md and
.agents/roles/product.md to orchestrate B08 / DOB-89.

Read the canonical B08 spec, available Linear parent/child issues,
pilot artifacts and current implementation. Report unavailable access.
Identify acceptance gaps, dependencies and unresolved contract decisions.
Prepare ordered briefs for cross-area planning, backend implementation,
Lovable prompt/source handoff, Flutter implementation and verification.
Each brief must name its scope, prerequisites, skills, criteria and checks.

This session is for planning and handoff preparation. Do not implement
product code, publish tickets, invoke other agents/models or deploy.
```

Open the recommended next agent with its brief. Gemini is the preferred cross-area planner; Sonnet is preferred for substantial React-to-Flutter work. These preferences are recorded in roles, not enforced by a model launcher. You may use a capable available agent while keeping the same role/skill instructions.

For B08's design path, review the [Lovable React prompt](../.specs/mvp-v0.1/pilot/lovable-staff-invitation.md), run Lovable yourself, then record the actual source directory/repository and immutable revision in the [source handoff](../.specs/mvp-v0.1/pilot/react-source-handoff.md). Give those artifacts to the heavy-UI agent. If the export is pending, translation remains blocked; independent backend work can proceed when its own prerequisites are met.

## Scenario 3: Use a CLI-generated handoff

From the root terminal with the workflow virtual environment active:

```sh
python -m tools.agent_workflow handoff --spec B08 --role backend \
  --output .agent-workflow/handoffs/B08-backend.md
```

Then open your backend agent and paste:

```text
Read .agent-workflow/handoffs/B08-backend.md and the canonical source
spec/skills it references. Implement only the backend assignment in
.specs/mvp-v0.1/pilot/implementation-tasks.md (DOB-91).
Check the current code, available issue context and prerequisites first;
the generated document is a snapshot, not a readiness certificate.
Proceed with independent work and report concrete blocked dependencies.
Run relevant checks and return evidence plus a frontend handoff.
Do not stage, commit, push, publish Linear changes or deploy.
```

A generated package includes the full journey, all spec skills, role instructions, dependency references and checks. Seeing frontend skills in a backend package does not expand the assignment to frontend implementation. Your prompt and scoped task define write ownership. The CLI does not produce a code-aware minimal plan.

Regenerate after spec/role/skill changes. Always read the canonical sources because generated copies can become stale, including their relative Markdown links. Runtime packages under `.agent-workflow/` are ignored; durable decisions belong in specs/docs and tracked issues. A handoff for `cross-repo-planner` requests planning; a handoff for `heavy-ui` can still have missing source prerequisites. The filename alone never means ready for implementation.

For platform work, include the catalog option before the command:

```sh
python -m tools.agent_workflow --catalog platform handoff \
  --spec P01 --role cross-repo-planner \
  --output .agent-workflow/handoffs/P01-plan.md
```

## Scenario 4: Fix a bug without an orchestrator

Choose your bug-fix agent and paste this example, substituting an actually observed failure and reproduction:

```text
Investigate and fix a cashier operating-day expiry regression in the
DOB-85 / B05 area, if reproducible on this checkout.
Expected behavior: B05-AC05. Observed behavior: [describe failure].
Reproduction/environment: [steps, venue hours/timezone, timestamps].

Read AGENTS.md, be/AGENTS.md and:
- .agents/skills/dobar-bugfix/SKILL.md
- .agents/skills/dobar-backend/SKILL.md
- .agents/skills/dobar-validation/SKILL.md

Read the issue if available; report missing access. Reproduce before
editing, identify the cause, make a narrow compatible correction and
run a meaningful regression check. If it does not reproduce, report
the evidence rather than forcing a patch. Reuse/refine B05 in place
if acceptance needs clarification. Use dobar-communication-docs if
the boundary behavior changes. Do not commit, push or deploy.
```

A bounded bug needs no orchestration session. If diagnosis reveals several incompatible contracts or an unresolved product decision, return that specific finding and request a planning decision; do not silently turn the fix into a broad refactor.

## Scenario 5: Independently verify implementation

Use a fresh verifier chat with access to the same checkout and implementation evidence:

```text
Use .agents/skills/dobar-validation/SKILL.md to independently verify
the implemented backend scope for B08 / DOB-91 on this checkout.
Read the current spec, implementation diff and author's check evidence.
Run meaningful available checks and map each assigned criterion to
passed, failed, blocked or skipped evidence. Mark criteria requiring
the remaining frontend/product journey as incomplete where applicable.
Do not repair product code, publish issues or claim whole-journey
validation from backend-only checks. Return actionable follow-ups.
```

The verifier can run the check registry and save its report:

```sh
python -m tools.agent_workflow verify --spec B08 \
  --output .agent-workflow/reports/B08.json
```

`validate` checks artifact consistency. `verify` runs only the commands configured for that spec in the registry; it does not discover/run every test or use an LLM to assess criteria. Currently unconfigured journey/provider/device checks report blocked. Run affected-area checks separately and attach their results; they do not silently replace required E2E evidence. Reports do not update spec or Linear state automatically.

## A reusable starting prompt

```text
Task: [concrete outcome]. Issue/spec: [ID and path].
Mode: [plan only / implement / independently verify].
Scope: [owned areas/files and acceptance criteria].
Read AGENTS.md, affected-area instructions and [explicit skill paths].
Read the linked Linear issue if available; report missing access.
Inspect actual code and dependencies; continue within authorized scope.
Run the appropriate checks and report evidence and remaining blockers.
Preserve user changes; do not publish tickets or Git changes or deploy.
```

Replace the publication boundary only when you intend to authorize a specific external action. Choose the mode explicitly: an implementation prompt can carry work through code and checks, while a planning prompt ends with reviewable tasks/handoffs.
